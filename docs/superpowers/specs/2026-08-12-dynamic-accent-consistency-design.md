# 动态强调色一致性修复设计

## 状态

用户已于 2026-08-12 批准本设计的行为范围，等待书面规格复核后进入实施计划。

## 目标

修复 KDE 壁纸同步模式下动态强调色的状态一致性问题：

1. 服务重启后，同一壁纸恢复与重启前一致的颜色。
2. 单块屏幕执行 A → B → A 时可靠恢复 A 的颜色。
3. 每张可解码壁纸都会触发有效取色或明确回退，不会无故继承上一张壁纸的颜色。
4. 多块屏幕使用不同壁纸时，各自独立显示对应强调色。
5. 每块屏幕的信息卡与音频频谱带使用该屏幕自己的动态色，并同步过渡。
6. 音频频谱的左右声道分别使用强调色和互补色，双声道合并曲线根据当前壁纸亮度使用纯黑或纯白，避免在极亮或极暗壁纸上失去可读性。
7. 指针交互结束后，renderer 必须在不改变 `motion.returnSpeed` 或相机回归轨迹的前提下可靠恢复到漂移帧率。

## 已确认根因

当前实现把壁纸更新与颜色分析请求作为两个独立 IPC 事件发布。Renderer 可能先解码新图片、后收到颜色请求，或先收到请求、后完成另一张图片的解码；`loadedWallpaperUrl`、当前图片和颜色 generation 并不属于同一原子快照，因此快速切换时存在旧图片颜色提交给新身份或遗漏分析的竞态。

颜色缓存目前每块屏幕只保存最后一次壁纸颜色，并以 Electron display ID 命名。A → B 会覆盖 A 的缓存，返回 A 时必须重新分析；Electron display ID 在拓扑或进程生命周期中还可能变化，使重启后的缓存命中不稳定。现场数据也显示同一壁纸副本曾在不同屏幕得到不一致结果，符合异步请求与图片错配的表现。

音频频谱带当前虽然已经从每屏强调色派生三种亮度，但三个角色仍属于同一色相，不能表达已确认的“强调色、互补色、中性色”语义。中性色若固定为灰色或固定为白色，也会在部分壁纸上缺少足够对比。

运动状态机当前只有在相机连续 `0.2s` 同时满足位置、速度、旋转和缩放误差阈值时，才从 `returning` 切回 `drift`。但是回归目标 `driftReference` 始终沿漂移轨迹移动；使用默认 `returnSpeed: 0.3` 真实模拟交互后，即使运行 `30s` 仍无法满足全部阈值，状态永久停在 `returning`，目标帧率也永久保持 `frameRate.interactive`。现有测试逐帧把相机强制复制为漂移参考，因此没有覆盖真实回归。

## 推荐架构

采用“全局按壁纸内容缓存 + 每屏独立当前状态 + 单一事务更新”。不采用单纯增加防抖或延迟，因为它只能降低竞态概率；也不继续使用纯 display ID 缓存，因为它无法可靠处理 A → B → A、重启和显示器 ID 变化。

### 壁纸内容标识

每个已验证的受管理壁纸产生确定性的内容键。内容键必须代表实际图片内容，而不是显示器编号或缓存目标路径。优先复用导入流程计算的文件摘要；若当前导入元数据没有摘要，则在文件发生变化并完成验证时计算一次 SHA-256，并持久化到壁纸 metadata/status 中。

内容键格式包含版本与摘要，例如 `sha256:<hex>`。相同图片即使来自不同源路径或被复制到不同显示器缓存，也得到相同内容键；内容变化即使路径、大小或粗粒度 mtime 碰巧相同，也得到不同内容键。

### 全局颜色缓存

颜色缓存改为按内容键保存：

```text
${XDG_DATA_HOME:-$HOME/.local/share}/mip-paper/colors/by-content/<sha256>.json
```

记录包含缓存版本、内容键、已校验 RGB、壁纸感知亮度、算法版本和更新时间。感知亮度使用 sRGB 线性化后的相对亮度，范围为 `0–1`。算法版本参与有效性判断，以便未来修改取色或亮度算法后主动重算，而不是永久继承旧结果。

同一图片用于多块屏幕时共享分析结果，保证颜色一致且避免重复分析。不同图片使用不同缓存项。旧的 `<display-id>.json` 缓存不再作为权威颜色来源；升级时可安全忽略，不把可能错配的历史结果迁入内容缓存。

### 每屏独立状态

颜色服务仍为每个当前显示器维护独立 record：

- 当前 `wallpaperIdentity`；
- 当前 `contentKey`；
- 单调递增的 generation；
- 当前壁纸颜色或等待分析状态；
- 最后一次可展示的回退颜色；
- 当前发布给该屏 renderer 的颜色状态。

全局缓存只回答“某张图片的颜色是什么”，不决定哪块屏幕正在使用它。颜色服务按各屏当前内容键独立选择和发布颜色。因此两块屏幕使用不同壁纸时颜色不同；使用相同壁纸时从同一缓存恢复相同颜色。

显示器增加、移除或 ID 变化时，当前 KDE 同步结果重新绑定到新的每屏 record。只要内容键相同，即可从全局缓存恢复颜色，不依赖旧 display ID。

## 原子更新契约

壁纸同步服务对某块屏幕发布一个完整事务，而不是分别发布 URL 和随后补发 identity：

```js
{
  wallpaperUrl,
  wallpaperIdentity,
  contentKey,
  generation,
  color,
  wallpaperLuminance
}
```

其中 `color` 是颜色服务针对该内容键生成的当前状态，可能是已缓存壁纸色，也可能带有 `analyzeWallpaper: true` 的分析请求；`wallpaperLuminance` 是同一次壁纸采样得到的感知亮度。Window manager 在同一个屏幕窗口的 bootstrap 与更新事件中保存并发送这份完整快照。缓存缺少亮度的旧记录视为需要重新分析，避免沿用无法决定黑白中性色的不完整结果。

Renderer 接收事务后：

1. 为该事务启动图片解码。
2. 只有事务 generation 仍为最新时，才把图片提升为当前图片。
3. 若事务包含有效缓存色，图片提升时同时应用该颜色。
4. 若需要分析，只分析该事务刚解码的图片；同一次采样同时产生强调色和感知亮度，并原样提交其 content key、identity 和 generation。
5. 主进程只有在三项均仍匹配该屏当前 record 时才接受结果。
6. 任意迟到的解码、分析或提交结果均被丢弃，不能改变当前屏幕颜色。

启动也使用同一事务路径。窗口创建前，KDE 同步先完成内容标识与缓存查询，因此 bootstrap 不会先显示一个无身份的默认颜色，再用偶然完成的分析覆盖。

## A → B → A 行为

- 首次 A：无内容缓存时分析 A，保存 `A-key → A-color`。
- 切换 B：当前屏 generation 增加；A 的任何迟到结果失效。若 B 无缓存则分析 B并保存。
- 返回 A：通过 A 的内容键立即命中 `A-color`，无需依赖当前屏最后缓存，也无需重新分析。
- 另一块屏幕仍使用 B 时继续保持 B 的独立颜色，不受 A 屏切换影响。

## 分析失败与回退

图片成功解码但 Canvas 取色失败、返回空值或提交失败时，不把旧颜色标记为新壁纸的壁纸色，也不写入内容缓存。

回退遵循现有模式语义：

- `default`：默认粉色。
- `kde`：KDE 强调色，再到默认粉色。
- `wallpaper`：该屏最后一次可展示颜色，再到默认粉色，但状态来源明确标为 fallback，不伪装成当前壁纸分析成功。
- `hybrid`：当前壁纸缓存/分析色、KDE 强调色、该屏最后一次可展示颜色、默认粉色。

失败状态保留 `analyzeWallpaper: true` 的可重试能力。后续同一事务的 renderer 重建、显示器重协调或明确颜色刷新可以再次分析；同一次失败不会形成无界忙循环。日志记录屏幕、generation 和脱敏后的失败类别，不输出图片像素。

## 音频频谱动态色

音频频谱继续保留三层视觉层级，并使用三个语义明确的每屏颜色角色：

- 右声道使用当前壁纸强调色 `--accent-audio-primary`；
- 左声道使用 `--accent-audio-complement`，由强调色在 HSL 色相环旋转 `180°` 得到，并保留经过可用性约束后的饱和度与亮度；
- 双声道合并曲线使用 `--accent-audio-neutral`，值只能是纯黑 `rgb(0 0 0)` 或纯白 `rgb(255 255 255)`，不使用灰色；
- 三条线的 stroke、必要的 glow/filter 均使用 `--accent-transition-ms`；
- reduced motion 时颜色立即切换。

黑白中性色按当前屏幕壁纸的相对亮度选择。分别计算纯黑和纯白相对于壁纸亮度的 WCAG 对比度，选取较高者；两者相等时选择纯黑。精确比较的分界约为相对亮度 `0.1791288`：高于或等于该值使用黑色，低于该值使用白色。这使纯白壁纸稳定选择黑色，纯黑壁纸稳定选择白色，且选择结果不依赖强调色本身的明暗。

三个角色和壁纸亮度由 `applyAccentState` 一次设置，避免音频控制器另存颜色状态。每个屏幕有独立 document root，并从自己的壁纸事务获得强调色与亮度，因此不同壁纸的屏幕可独立选择互补色和黑/白中性色。若已解码图片的亮度分析意外失败，该屏保留最后一次有效的黑/白中性色；进程首次启动且尚无有效亮度时沿用纯白作为短暂回退，成功分析后立即校正。

## 漂移帧率恢复

运动状态仍保留 `drift → interactive → returning → drift` 的三状态循环。有效指针输入后进入 `interactive`；最后一次有效输入结束 `0.95s` 后进入 `returning`。原有 `motion.returnSpeed` 弹簧、移动 `driftReference`、误差阈值和 `settledDuration` 完成判定全部保持不变。

帧率恢复与运动完成解耦。`returning` 使用独立的 `returnElapsed` 记录本轮回归已经持续的时间：

- 进入 `returning` 时将 `returnElapsed` 清零；
- 每个固定模拟步只按原有 `motion.returnSpeed` 弹簧追踪持续移动的 `driftReference`，不增加插值、不提高弹簧频率、不强制对齐相机；
- `returnElapsed` 小于 `1.5s` 时请求 `frameRate.interactive`；达到 `1.5s` 后仅请求 `frameRate.drift`，相机仍保持 `returning` 并按原速继续回归；
- 原有误差条件若未来自然满足，状态照常从 `returning` 切到 `drift`；帧率计时不参与该状态转换；
- 回归期间收到新的有效指针输入时立即切回 `interactive` 并清零 `returnElapsed`，之后重新执行完整回归；
- `interactionEnabled` 热切换为关闭时，清除指针输入状态；若当前处于交互或回归阶段，仍通过原有自然回归路径继续运动，不建立另一套状态转换。

调度器继续在每个 callback 根据 `requestedFrameRate` 查询目标帧率。回归帧率保持窗口结束后，下一次调度判断必须采用 `frameRate.drift` 并重置绘制累计/截止时间；不重启 scheduler，也不新增独立定时器。性能探针的 `return` 场景必须实际注入一次指针交互，并观察 `interactive`、`returning` 以及最终漂移目标帧率，不能把一个从未进入交互态的 idle renderer 标记为 return。

## 测试策略

遵循 TDD，先加入能够复现当前缺陷的失败测试，再修改实现。

### 颜色服务

- A → B → A 从内容缓存恢复 A，且 B 不覆盖 A。
- 两块屏幕使用不同内容键，分别发布不同 RGB。
- 两块屏幕使用相同内容键，共享一次缓存结果并得到相同 RGB。
- 重建服务并更换 display ID 后，相同内容键仍恢复相同颜色。
- generation、identity 或 content key 任一不匹配时拒绝迟到提交。
- 分析失败不把旧色写成当前壁纸色，并保留受控重试状态。
- 损坏缓存、旧算法版本和无效 RGB 被忽略。
- 感知亮度随内容键缓存；缺失、非有限值或超出 `0–1` 的亮度使缓存失效并触发重新分析。

### 壁纸同步与 Window manager

- 每次更新以单一事务携带 URL、identity、content key、generation 和颜色状态。
- 不同屏幕只收到自己的事务。
- bootstrap 与实时更新使用相同结构。
- 快速连续 A/B 更新时，旧事务不能覆盖新 bootstrap 或窗口状态。

### Renderer

- B 先完成、A 后完成时只提升 B；A 的分析结果不提交。
- 颜色请求先于或晚于图片解码时都绑定到同一事务图片。
- 返回已缓存的 A 时在图片提升时立即应用 A 色。
- 每个 renderer 只应用其自身屏幕事务。
- 同一次 Canvas 采样同时返回强调色和壁纸感知亮度，不进行第二次图片解码或独立异步采样。

### 运动状态与调度器

- 使用默认配置完整模拟一次真实指针交互，不手工复制相机状态；多个时间点的全部相机字段必须逐字段等同修改前的 `motion.returnSpeed: 0.3` 轨迹。
- `returning` 开始后的前 `1.5s` 请求交互帧率，之后在不改变 mode 或运动轨迹的情况下请求漂移帧率。
- 回归中再次输入会重置回归计时，不能沿用旧进度提前完成。
- 不允许新增 smoothstep、额外插值、强制相机对齐或修改 `motion.returnSpeed`。
- adaptive scheduler 覆盖真实 `interactive → returning` 状态变化，并验证回归帧率保持窗口结束后的绘制节拍降至 `frameRate.drift`。
- `interactionEnabled` 从开启热切换为关闭后沿原轨迹自然回归，并在保持窗口结束后恢复漂移帧率。
- 性能探针的 `return` 场景验证确实观察到交互与回归状态，并最终报告漂移目标帧率，否则该次结果无效。

### 音频频谱与 CSS

- 右声道引用强调色，左声道引用 HSL `180°` 互补色，双声道合并曲线只引用纯黑/纯白中性色。
- 纯白、纯黑及亮度分界两侧的壁纸样本会得到确定且对比度更高的黑/白选择。
- 两块屏幕亮度不同时，各自独立选择黑色或白色，不共享 renderer 状态。
- 角色更新使用配置过渡时间，reduced motion 使用 0 ms。
- 切换壁纸颜色时无需重建 audio controller。

## 验收

自动验证：

```bash
npm test
npm run check
bash -n bin/mip-paper scripts/kwin-rules.sh scripts/kwin-script.sh
npm audit
npm audit --omit=dev
git diff --check
```

实机验证：

1. 两块屏幕分别选择明显不同的壁纸，确认卡片和音频频谱分别使用不同颜色。
2. 单屏执行 A → B → A，确认返回 A 后稳定恢复原颜色。
3. 在 A 状态执行 `mip-paper restart`，确认颜色不改变。
4. 快速连续切换多张壁纸，确认没有旧壁纸颜色迟到覆盖。
5. 使用灰暗、接近纯黑/纯白及普通彩色壁纸，确认均产生颜色或明确进入回退，而非无状态继承。
6. 播放系统音频并切换壁纸，确认左右声道分别使用强调色与互补色，合并曲线在浅色壁纸上为纯黑、深色壁纸上为纯白，三者平滑更新且运动不中断。
7. 移动指针触发视差后停止输入，确认约 `0.95s` 后按原有速率开始回归；回归 `1.5s` 后绘制节拍恢复为配置的漂移帧率，但运动速度和轨迹没有变化。
8. 回归途中再次移动指针，确认立即重新跟随；再次停止后重新计算帧率保持窗口，且两次回归均保持原有 `motion.returnSpeed` 曲线。

## 非目标

- 不改变动态色的四种用户配置模式及其默认值。
- 不支持 KDE 幻灯片或第三方动态壁纸插件。
- 不重新设计信息卡布局、音频频谱几何或运动行为。
- 不把颜色状态扩展为跨用户或网络同步。
- 不引入新的取色 npm 依赖。
