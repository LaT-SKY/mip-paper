# 动态强调色一致性修复设计

## 状态

用户已于 2026-08-12 批准本设计的行为范围，等待书面规格复核后进入实施计划。

## 目标

修复 KDE 壁纸同步模式下动态强调色的状态一致性问题：

1. 服务重启后，同一壁纸恢复与重启前一致的颜色。
2. 单块屏幕执行 A → B → A 时可靠恢复 A 的颜色。
3. 每张可解码壁纸都会触发有效取色或明确回退，不会无故继承上一张壁纸的颜色。
4. 多块屏幕使用不同壁纸时，各自独立显示对应强调色。
5. 每块屏幕的信息卡与音频频谱带使用该屏幕自己的动态色，并同步过渡。

## 已确认根因

当前实现把壁纸更新与颜色分析请求作为两个独立 IPC 事件发布。Renderer 可能先解码新图片、后收到颜色请求，或先收到请求、后完成另一张图片的解码；`loadedWallpaperUrl`、当前图片和颜色 generation 并不属于同一原子快照，因此快速切换时存在旧图片颜色提交给新身份或遗漏分析的竞态。

颜色缓存目前每块屏幕只保存最后一次壁纸颜色，并以 Electron display ID 命名。A → B 会覆盖 A 的缓存，返回 A 时必须重新分析；Electron display ID 在拓扑或进程生命周期中还可能变化，使重启后的缓存命中不稳定。现场数据也显示同一壁纸副本曾在不同屏幕得到不一致结果，符合异步请求与图片错配的表现。

音频频谱带当前只有右声道线条使用 `--accent`；能量线和左声道仍是固定青色与白色，因此没有完整接受动态颜色体系。

## 推荐架构

采用“全局按壁纸内容缓存 + 每屏独立当前状态 + 单一事务更新”。不采用单纯增加防抖或延迟，因为它只能降低竞态概率；也不继续使用纯 display ID 缓存，因为它无法可靠处理 A → B → A、重启和显示器 ID 变化。

### 壁纸内容标识

每个已验证的受管理壁纸产生确定性的内容键。内容键必须代表实际图片内容，而不是显示器编号或缓存目标路径。优先复用导入流程计算的文件摘要；若当前导入元数据没有摘要，则在文件发生变化并完成验证时计算一次 SHA-256，并持久化到壁纸 metadata/status 中。

内容键格式包含版本与摘要，例如 `sha256:<hex>`。相同图片即使来自不同源路径或被复制到不同显示器缓存，也得到相同内容键；内容变化即使路径、大小或粗粒度 mtime 碰巧相同，也得到不同内容键。

### 全局颜色缓存

颜色缓存改为按内容键保存：

```text
${XDG_DATA_HOME:-$HOME/.local/share}/mip-paper/colors/by-content/<sha256>.json
```

记录包含缓存版本、内容键、已校验 RGB、算法版本和更新时间。算法版本参与有效性判断，以便未来修改取色算法后主动重算，而不是永久继承旧结果。

同一图片用于多块屏幕时共享分析结果，保证颜色一致且避免重复分析。不同图片使用不同缓存项。旧的 `<display-id>.json` 缓存不再作为权威颜色来源；升级时可安全忽略，不把可能错配的历史结果迁入内容缓存。

### 每屏独立状态

颜色服务仍为每个当前显示器维护独立 record：

- 当前 `wallpaperIdentity`；
- 当前 `contentKey`；
- 单调递增的 generation；
- 当前壁纸颜色或等待分析状态；
- 最后一次可展示的回退颜色；
- 当前发布给该屏 renderer 的颜色状态。

全局缓存只回答“某张图片的颜色是什么”，不决定哪块屏幕正在使用它。颜色服务按各屏当前内容键独立选择和发布颜色。因此两块屏幕使用不同壁纸时颜色不同；使用相同壁纸时从同一缓存恢复相同颜色。

显示器增加、移除或 ID 变化时，当前 KDE 同步结果重新绑定到新的每屏 record。只要内容键相同，即可从全局缓存恢复颜色，不依赖旧 display ID。

## 原子更新契约

壁纸同步服务对某块屏幕发布一个完整事务，而不是分别发布 URL 和随后补发 identity：

```js
{
  wallpaperUrl,
  wallpaperIdentity,
  contentKey,
  generation,
  color
}
```

其中 `color` 是颜色服务针对该内容键生成的当前状态，可能是已缓存壁纸色，也可能带有 `analyzeWallpaper: true` 的分析请求。Window manager 在同一个屏幕窗口的 bootstrap 与更新事件中保存并发送这份完整快照。

Renderer 接收事务后：

1. 为该事务启动图片解码。
2. 只有事务 generation 仍为最新时，才把图片提升为当前图片。
3. 若事务包含有效缓存色，图片提升时同时应用该颜色。
4. 若需要分析，只分析该事务刚解码的图片，并原样提交其 content key、identity 和 generation。
5. 主进程只有在三项均仍匹配该屏当前 record 时才接受结果。
6. 任意迟到的解码、分析或提交结果均被丢弃，不能改变当前屏幕颜色。

启动也使用同一事务路径。窗口创建前，KDE 同步先完成内容标识与缓存查询，因此 bootstrap 不会先显示一个无身份的默认颜色，再用偶然完成的分析覆盖。

## A → B → A 行为

- 首次 A：无内容缓存时分析 A，保存 `A-key → A-color`。
- 切换 B：当前屏 generation 增加；A 的任何迟到结果失效。若 B 无缓存则分析 B并保存。
- 返回 A：通过 A 的内容键立即命中 `A-color`，无需依赖当前屏最后缓存，也无需重新分析。
- 另一块屏幕仍使用 B 时继续保持 B 的独立颜色，不受 A 屏切换影响。

## 分析失败与回退

图片成功解码但 Canvas 取色失败、返回空值或提交失败时，不把旧颜色标记为新壁纸的壁纸色，也不写入内容缓存。

回退遵循现有模式语义：

- `default`：默认粉色。
- `kde`：KDE 强调色，再到默认粉色。
- `wallpaper`：该屏最后一次可展示颜色，再到默认粉色，但状态来源明确标为 fallback，不伪装成当前壁纸分析成功。
- `hybrid`：当前壁纸缓存/分析色、KDE 强调色、该屏最后一次可展示颜色、默认粉色。

失败状态保留 `analyzeWallpaper: true` 的可重试能力。后续同一事务的 renderer 重建、显示器重协调或明确颜色刷新可以再次分析；同一次失败不会形成无界忙循环。日志记录屏幕、generation 和脱敏后的失败类别，不输出图片像素。

## 音频频谱动态色

音频频谱继续保留三层视觉层级，但全部派生自该 renderer 根节点上的每屏颜色变量：

- 主强调线使用 `--accent`；
- 能量线使用由强调色生成的较亮角色；
- 辅助线使用低饱和、较亮的强调色角色；
- 三条线的 stroke、必要的 glow/filter 均使用 `--accent-transition-ms`；
- reduced motion 时颜色立即切换。

新增的角色由 `applyAccentState` 一次设置，避免音频控制器另存颜色状态。每个屏幕有独立 document root，因此天然消费该屏自己的动态色。

## 测试策略

遵循 TDD，先加入能够复现当前缺陷的失败测试，再修改实现。

### 颜色服务

- A → B → A 从内容缓存恢复 A，且 B 不覆盖 A。
- 两块屏幕使用不同内容键，分别发布不同 RGB。
- 两块屏幕使用相同内容键，共享一次缓存结果并得到相同 RGB。
- 重建服务并更换 display ID 后，相同内容键仍恢复相同颜色。
- generation、identity 或 content key 任一不匹配时拒绝迟到提交。
- 分析失败不把旧色写成当前壁纸色，并保留受控重试状态。
- 损坏缓存、旧算法版本和无效 RGB 被忽略。

### 壁纸同步与 Window manager

- 每次更新以单一事务携带 URL、identity、content key、generation 和颜色状态。
- 不同屏幕只收到自己的事务。
- bootstrap 与实时更新使用相同结构。
- 快速连续 A/B 更新时，旧事务不能覆盖新 bootstrap 或窗口状态。

### Renderer

- B 先完成、A 后完成时只提升 B；A 的分析结果不提交。
- 颜色请求先于或晚于图片解码时都绑定到同一事务图片。
- 返回已缓存的 A 时在图片提升时立即应用 A 色。
- 每个 renderer 只应用其自身屏幕事务。

### 音频频谱与 CSS

- 三层频谱线都引用动态强调色角色。
- 角色更新使用配置过渡时间，reduced motion 使用 0 ms。
- 切换壁纸颜色时无需重建 audio controller。

## 验收

自动验证：

```bash
npm test
npm run check
bash -n bin/mip-paper scripts/kwin-rules.sh scripts/kwin-script.sh
npm audit
npm audit --omit=dev
git diff --check
```

实机验证：

1. 两块屏幕分别选择明显不同的壁纸，确认卡片和音频频谱分别使用不同颜色。
2. 单屏执行 A → B → A，确认返回 A 后稳定恢复原颜色。
3. 在 A 状态执行 `mip-paper restart`，确认颜色不改变。
4. 快速连续切换多张壁纸，确认没有旧壁纸颜色迟到覆盖。
5. 使用灰暗、接近纯黑/纯白及普通彩色壁纸，确认均产生颜色或明确进入回退，而非无状态继承。
6. 播放系统音频并切换壁纸，确认三层频谱颜色平滑更新且运动不中断。

## 非目标

- 不改变动态色的四种用户配置模式及其默认值。
- 不支持 KDE 幻灯片或第三方动态壁纸插件。
- 不重新设计信息卡布局、音频频谱几何或运动行为。
- 不把颜色状态扩展为跨用户或网络同步。
- 不引入新的取色 npm 依赖。
