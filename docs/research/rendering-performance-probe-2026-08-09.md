# 渲染性能 Probe 结果（2026-08-09）

## 测试环境

- KDE Plasma 6 / KWin 6 / Wayland
- Electron 43.3.0
- 双显示器，当前桌面布局和用户配置未改变
- 运行快照已更新到仓库当前版本
- 原始结果：`/tmp/animated-ocean-probe-full.wfZog1`

每种策略依次执行 `idle`、`sweep`、`return` 三个场景。每个场景预热 30 秒、采样 60 秒。测试期间服务保持 `active`，结束后 probe 环境变量已清理。

## 有效绘制帧率

表中两个数值分别对应两块显示器。交互目标为 60 FPS，待机和回归目标为 30 FPS。

| 策略 | 待机 | 持续交互 | 回归 |
| --- | ---: | ---: | ---: |
| `raf` | 27.2 / 28.8 | 52.5 / 56.2 | 27.2 / 28.7 |
| `timer` | 30.0 / 30.0 | 60.0 / 60.0 | 30.0 / 30.0 |
| `adaptive` | 30.0 / 30.0 | 60.0 / 60.0 | 30.0 / 30.0 |

按当前 FPS 阈值，`raf` 未通过；`timer` 和 `adaptive` 的有效绘制帧率通过。

## 初步观察

- `raf` 在双屏实际 VSync 节奏下低于目标帧率，尤其是持续交互场景；固定 deadline 策略没有充分利用实际回调节奏。
- `timer` 和 `adaptive` 在三个场景中都保持目标绘制频率。
- 服务在策略切换、场景切换和最终恢复期间没有退出，窗口协调没有观察到异常。

## 数据质量限制

本轮结果不能直接用于选择默认策略：

1. renderer 尚未记录 callback interval 样本，因此 callback p95/p99 为 `null`，无法验证 20/33.4 ms 与 40/66.7 ms 的时序阈值。
2. probe 汇总中的 `mode` 在 collector 初始化时固定为 `drift`，不能区分持续交互阶段的真实模式。
3. `drawCount` 是累计值，当前结果需要按相邻汇总差值计算 FPS，不能直接对所有汇总求和。
4. `systemctl show` 的 CPU/RSS 采样目前是重启后的累计值和瞬时值，不能作为不同策略的归一化资源比较。

## 下一轮测试前置修正

- 在 scheduler 回调入口记录实际 callback interval，并在每个五秒汇总中输出 p50/p95/p99。
- 每次汇报时读取当前 `state.mode` 和 `requestedFrameRate(state, config)`，不在 collector 初始化时固定模式和目标帧率。
- 资源采样使用相邻采样差值：CPU 按时间窗口换算占用率，RSS 记录稳定窗口的中位数；标记服务重启边界，避免把启动开销混入场景数据。
- 修正后重新执行三种策略的完整 30 秒预热 + 60 秒采样协议，再决定默认策略。

本轮不修改默认调度策略。
