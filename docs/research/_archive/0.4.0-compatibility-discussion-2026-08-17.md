# Mip-Paper 0.4.0 Compatibility Discussion (Archived 2026-08-20)

> Archived from `0.4.0-compatibility-discussion.tmp.md` at 2026-08-17.
> Hyprland/GNOME/Niri targets are deferred in 0.4.0. Retained for traceability; do not implement.

## Confirmed Direction

- The primary 0.4.0 compatibility targets are Hyprland, GNOME, and Niri.
- KDE Plasma remains the known-good baseline and must continue to work.
- The release goal is **core-experience consistency**, not identical feature parity across every desktop environment.
- Core behavior should include, where the environment supports it:
  - dynamic wallpaper rendering;
  - stable desktop/background layering;
  - per-output display placement;
  - display hot-plug handling;
  - no unwanted focus or task-switcher presence;
  - orderly startup, shutdown, and recovery.
- Environment-specific capabilities may degrade, but the degradation must be explicit and diagnosable. Examples include desktop-wallpaper synchronization, fullscreen detection, and compositor-specific pause behavior.

## Integration Model

- Use a shared application/rendering core with desktop-environment adapters.
- Adapter components are allowed and expected where the desktop protocol requires them.
- The main distribution should include the supported adapters and detect the current desktop environment automatically.
- Setup must also be available as an explicit user command.
- The application must not silently install extensions, write compositor configuration, or enable desktop integration.
- Teardown must be explicit and must remove only Mip-Paper-owned integration.
- Missing optional integration must produce a useful `doctor`/diagnostic result and a defined fallback mode.

## Current Validation Sequence

1. Keep KDE Plasma on the host as the existing baseline.
2. Create a GNOME Boxes virtual machine for an initial Hyprland deployment.
3. Validate Hyprland feasibility before deploying additional target desktops.
4. After Hyprland is viable, extend the validation to GNOME and Niri.

The long-term release gate should cover all four environments in real Wayland sessions. The immediate milestone is only the Hyprland feasibility gate.

## Hyprland Decision

- The formal Hyprland direction is a native Wayland layer-shell adapter.
- Electron remains the renderer/business runtime in the current discussion model; it should not be responsible for implementing the layer-shell protocol directly.
- The native host should create one background-layer surface per output and own output geometry, scale, layer ordering, input policy, and lifecycle integration.
- The implementation language and exact IPC boundary are intentionally deferred for a later design discussion.
- Electron-window plus compositor-rule behavior may be used as a temporary feasibility comparison, but it is not the intended 0.4.0 Hyprland endpoint.
- XWayland windows may help isolate rendering experiments, but do not count as proof of native Wayland desktop-layer compatibility.

## Open Decisions

- Native host language and protocol libraries.
- Electron/native-host IPC and crash/restart behavior.
- Exact Hyprland acceptance matrix and VM image/version baseline.
- Niri adapter strategy and whether it can share the wlroots/layer-shell host.
- GNOME integration mechanism and the boundary of any GNOME Shell extension.
- Feature-by-feature downgrade semantics and user-visible diagnostics.
- Packaging of adapters, setup/teardown ownership, and upgrade/rollback rules.
- Final release gates, screenshots, logs, and reproducible VM snapshot procedure.
